# End-to-end publish flow

A single invocation — locally or in CI — follows a fixed sequence so failures are obvious early and the space does not accumulate stale autogenerated pages.

## Ordered steps

![Publish run: verify, search, delete, walk, create](/data_images/publish-pipeline.svg)

### 1. Verify parent page

The publisher **GET**s the configured parent page. Wrong URL, space, ID, or credentials fail here before any destructive work.

### 2. Search for existing published pages

A **CQL** query finds descendant pages tagged with the configured **content property** (for example `autogenerated-publisher` → JSON including `"publisher": "github-confluence-publisher"`).

### 3. Delete findings

Each matched page is **deleted**. This is the “full refresh” guarantee: what you see under the parent after a run reflects **only** the current Git tree (for pages this tool manages).

### 4. Walk the Markdown root

The walker uses `os.scandir` on `github_folder_with_md_files` (or `PUBLISHER_MARKDOWN_ROOT`):

- **Directory** → create a Confluence child page whose title matches the folder name, body = **Children Display** macro, then recurse with that page as the new parent.
- **`.md` file** → read file, process images, convert Markdown to HTML, prepend banner, create page, attach image files, set content property.
- **Other files** → skipped (logged).

### 5. Create content and attachments

For each Markdown page, local image references like `![alt](/data_images/diagram.svg)` are rewritten to Confluence storage XML referencing an attachment filename; the file is then uploaded if it exists under `github_folder_with_image_files`.

## Operational implication

Because step 3 removes all previously tagged pages, **do not** point the parent at a subtree where humans maintain long-lived manual pages without that property — they would not be selected by the property query, but mixing workflows under the same parent can still confuse editors. A dedicated “generated docs” parent is safest.
