# Configuration and banner

Runtime behavior is driven primarily by **`publisher/config/config.yaml`**, with environment variables overriding selected keys for pipelines and containers.

## Key YAML fields

```yaml
confluence_url: https://your-site.atlassian.net/wiki/rest/api/
confluence_space: YOURSPACE
counfluence_parent_page_id: "123456"   # typo preserved for backward compatibility
publisher_property_key: autogenerated-publisher
banner_repo_url: https://github.com/your-org/your-repo
banner_project_name: your-repo
github_folder_with_md_files: ./data_example
github_folder_with_image_files: ./data_example_images
```

| Key | Role |
|-----|------|
| `confluence_url` | Normalized to REST API base with trailing slash |
| `confluence_space` | Target space key |
| `counfluence_parent_page_id` | Parent page for the generated hierarchy |
| `publisher_property_key` | Content property key used for CQL + tagging |
| `github_folder_with_*` | Roots for Markdown walk and image attachments |
| `banner_*` | Injected HTML at top of each generated page |

## Banner

Every generated page gets a small **HTML banner** pointing editors back to the Git repository (`banner_repo_url` + `banner_project_name`). That reinforces “edit in Git, not in Confluence” for teams that treat Confluence as a read-only mirror.

## Example workspace layout

This repo’s **sample** paths (used by `config.yaml` in some setups):

- Markdown: `./data_example`  
- Images: `./data_example_images`  

Image references inside Markdown still use the **virtual** path `/data_images/filename` so the publisher’s line-based parser recognizes and rewrites them consistently (see the next section’s diagram in **03 Confluence integration**).
