# Publisher

## Purpose

Synchronize Markdown documentation from this repository to a Confluence Cloud space: verify configuration, remove previously autogenerated pages, and recreate pages and attachments so the wiki matches the Git tree. Runs inside a Docker container with proper TLS verification.

## Requirements

### Requirement: Configuration

The publisher MUST load Confluence connection settings, banner settings, and local paths from `publisher/config/config.yaml` and MUST allow overriding URL, space, parent page id, banner repo URL, and banner project name via environment variables when those variables are set.

#### Scenario: Environment overrides URL and space

- GIVEN `CONFLUENCE_URL` and/or `CONFLUENCE_SPACE` are set
- WHEN configuration is loaded
- THEN the effective `confluence_url` and/or `confluence_space` reflect the environment values after URL normalization

#### Scenario: Environment overrides banner settings

- GIVEN `BANNER_REPO_URL` and/or `BANNER_PROJECT_NAME` are set
- WHEN configuration is loaded
- THEN the effective banner fields reflect the environment values

### Requirement: Credential validation

The publisher MUST require a non-empty login (email) and password (API token) from CLI arguments or environment variables and MUST exit with an error if either is missing.

#### Scenario: Missing credentials

- GIVEN neither CLI nor environment provides both login and token
- WHEN the process starts
- THEN it logs an error and exits without calling Confluence

### Requirement: Parent page verification

Before searching or mutating content, the publisher MUST verify that the configured parent page exists via the Confluence REST API and MUST fail with a clear error if the page is missing or the API returns an error.

#### Scenario: Invalid parent id

- GIVEN the REST API returns 404 for the configured parent page id
- WHEN verification runs
- THEN the run fails with a message indicating the parent page was not found

### Requirement: Page identification via content properties

The publisher MUST tag each created page with a Confluence content property (key from `publisher_property_key`, default `autogenerated-publisher`) containing a JSON value with at minimum `{"publisher": "github-confluence-publisher"}`. Page titles MUST NOT include any visible identification suffix.

#### Scenario: Page is tagged on creation

- GIVEN a page is successfully created via the REST API
- WHEN the publisher receives the new page id
- THEN it POSTs a content property to `/rest/api/content/{id}/property` with the configured key and publisher identifier

#### Scenario: Page title stays clean

- GIVEN a Markdown file named `setup.md`
- WHEN the page is created
- THEN the Confluence page title does not contain any search-pattern suffix or machine-readable tag

### Requirement: Full refresh of autogenerated pages

The publisher MUST search the configured Confluence space for pages tagged with the publisher's content property, MUST delete each found page, and MUST then recreate the tree from the local Markdown folder so Confluence matches the repository.

#### Scenario: Prior run left autogenerated pages

- GIVEN pages exist in the space that carry the publisher's content property
- WHEN a publish run completes
- THEN those pages are removed before new pages are created from disk

#### Scenario: Legacy pages from prior versions

- GIVEN pages exist that were created by a previous version using the text-based search pattern (title suffix) and no content property
- WHEN the first publish run after upgrade executes
- THEN the publisher falls back to a text-based CQL search, deletes those legacy pages, and recreates them with content-property tagging

### Requirement: Folder mirroring

For each directory under the configured Markdown root, the publisher MUST create a Confluence page titled like the directory, MUST set its body to a Children Display macro, MUST tag it with the content property, and MUST publish nested files under that page as children.

#### Scenario: Nested folders

- GIVEN `data/a/b/page.md` exists
- WHEN publishing completes
- THEN Confluence has a hierarchy of folder pages under the configured parent with `page.md` as a descendant at the correct depth

### Requirement: Markdown and local images

For each `.md` file, the publisher MUST convert Markdown to HTML (including tables and fenced code where supported), MUST replace local image markdown with Confluence storage references to attachments, and MUST upload matching files from the configured image folder as attachments on the created page.

#### Scenario: Local image path

- GIVEN a line contains a local image reference (not `http` or `https`)
- WHEN the page is created
- THEN the image file is attached when it exists under `github_folder_with_image_files` and the page body references the attachment

### Requirement: Non-Markdown files

The publisher MUST NOT create Confluence pages from non-`.md` files in the tree; it MAY log that such files were skipped.

#### Scenario: Other file types

- GIVEN a `.txt` file exists beside Markdown files
- WHEN the folder is published
- THEN no Confluence page is created from that file

### Requirement: SSL / TLS verification

All HTTP calls to the Confluence REST API MUST use the system TLS trust store for certificate verification. The publisher MUST NOT disable certificate verification. Custom CA certificates MUST be supported via the Docker container's certificate mount point or the `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE` environment variables.

#### Scenario: Valid certificate

- GIVEN the Confluence instance presents a certificate trusted by the system CA store
- WHEN any REST API call is made
- THEN the request succeeds with full TLS verification

#### Scenario: Custom corporate CA

- GIVEN a custom CA certificate is mounted into the container at `/usr/local/share/ca-certificates/custom/`
- WHEN the container starts
- THEN `update-ca-certificates` incorporates the custom cert and subsequent API calls trust it

#### Scenario: Untrusted certificate

- GIVEN the Confluence instance presents a certificate not trusted by the system CA store and no custom CA is provided
- WHEN a REST API call is made
- THEN the request fails with a TLS verification error

### Requirement: Docker container

The publisher MUST be packaged as a Docker container based on `python:3.14-slim` that bundles all dependencies and CA certificates. The container MUST accept all runtime inputs (Confluence connection, credentials, banner settings, source paths) as environment variables or mounted volumes.

#### Scenario: Container runs with environment variables

- GIVEN `CONFLUENCE_URL`, `CONFLUENCE_SPACE`, `CONFLUENCE_PARENT_PAGE_ID`, `CONFLUENCE_LOGIN`, and `CONFLUENCE_API_TOKEN` are passed as environment variables
- WHEN the container starts
- THEN the publisher runs using those values without requiring a config file override

#### Scenario: Custom CA certs mounted

- GIVEN a volume with `.crt` files is mounted to `/usr/local/share/ca-certificates/custom/`
- WHEN the container starts
- THEN `update-ca-certificates` runs before the publisher and the custom certs are trusted

### Requirement: Configurable banner

Created pages MUST include an HTML banner at the top of the page body. The banner text, repository URL, and project name MUST be configurable via `banner_repo_url` and `banner_project_name` in the config file, overridable by `BANNER_REPO_URL` and `BANNER_PROJECT_NAME` environment variables.

#### Scenario: Custom banner values

- GIVEN `banner_repo_url` is `https://github.com/my-org/my-repo` and `banner_project_name` is `My Project`
- WHEN a page is created
- THEN the page body starts with a banner containing a link to `https://github.com/my-org/my-repo` with text `My Project`

#### Scenario: Default banner values

- GIVEN no banner config or environment variables are set
- WHEN a page is created
- THEN the page body includes a banner with sensible default text
