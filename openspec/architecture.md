# Architecture

This document describes how the GitHub to Confluence publisher works end to end, which technologies it uses, and how configuration flows through the system.

## Tech stack

| Layer | Technology | Role |
|--------|------------|------|
| Runtime | Python 3.14 | CLI entry point and automation |
| Packaging | Docker (`python:3.14-slim` + `ca-certificates`) | Reproducible environment with proper TLS trust store |
| HTTP / API | `requests`, `urllib3` | Confluence Cloud REST API (pages, properties, search, delete, attachments) |
| Auth | HTTP Basic | Atlassian account email + API token (token as password) |
| Markdown | `markdown` (with tables, fenced code) | Convert `.md` body to HTML before Confluence storage format |
| Configuration | `PyYAML` | `publisher/config/config.yaml`; optional env overrides |
| Version control & CI | Git, GitHub Actions (`ubuntu-latest`) | Checkout, build Docker image, publish on `main` |

Pinned dependency versions live in `publisher/requirements.txt`.

## Repository layout (runtime-relevant)

- `publisher/` — application code (`main.py`, `pagesController.py`, `pagesPublisher.py`, `config/`).
- `data/` — default tree of Markdown (and folder structure mirrored in Confluence).
- `data_images/` — images referenced from Markdown (local paths, not `http`/`https`).
- `Dockerfile` — container definition; bundles the publisher, dependencies, and CA certificates.
- `.github/workflows/publisher.yml` — CI job that builds the Docker image and runs the publisher when secrets are available.

## Process definition

### 1. Configuration

1. Load `publisher/config/config.yaml` (space key, parent page id, REST API base URL, publisher property key, banner settings, local folder paths).
2. Normalize `confluence_url` to the Confluence REST API base (trailing slash, `/wiki/rest/api/`).
3. Apply environment overrides when set: `CONFLUENCE_URL`, `CONFLUENCE_SPACE`, `CONFLUENCE_PARENT_PAGE_ID`, `BANNER_REPO_URL`, `BANNER_PROJECT_NAME`.

### 2. Credentials

Credentials are not stored in the repo. They are supplied via:

- CLI: `--login` (email) and `--password` (API token), or
- Environment: `CONFLUENCE_LOGIN` and `CONFLUENCE_API_TOKEN`.

GitHub Actions maps repository secrets into these variables for automated runs. The Docker container receives them as `--env` flags.

### 3. Publish run (single execution)

The following sequence runs for each invocation (inside the Docker container or directly):

1. **Verify parent page** — GET the configured parent page via the REST API to fail fast on wrong URL, id, or auth.
2. **Search** — CQL query using Confluence **content properties** to find pages previously tagged by this publisher: `type = page AND space = "<SPACE>" AND ancestor = <PARENT_ID> AND content.property[<KEY>].publisher = "github-confluence-publisher"`.
3. **Delete** — DELETE each found page so the next publish reflects the current Git tree (full refresh of generated content under the parent).
4. **Publish tree** — Walk `github_folder_with_md_files` recursively from the repository root:
   - **Directory** — Create a Confluence child page titled like the folder, with a Children Display macro as body; tag the page with a content property; recurse with that page as parent.
   - **Markdown file** — Read `.md`, rewrite local image references to Confluence `ac:image` / attachment placeholders, convert the rest with Markdown to HTML, prepend the configurable banner, create a page under the current parent, tag the page with a content property, then attach referenced files from `github_folder_with_image_files` when present.
   - **Non-Markdown files** — Logged and skipped for publishing.

### 4. Page identification via content properties

Each created page is tagged with a Confluence **content property** (a hidden key/value JSON object attached to a page, invisible to readers, queryable via CQL).

- **Key**: configurable via `publisher_property_key` (default: `autogenerated-publisher`).
- **Value**: JSON object containing at minimum `{"publisher": "github-confluence-publisher"}`.
- **API**: `POST /rest/api/content/{id}/property` after page creation.

Page titles remain clean — no visible suffix or pattern is appended.

### 5. SSL / TLS verification

All `requests` calls use the system TLS trust store (no `verify=False`). The Docker image installs `ca-certificates` and runs `update-ca-certificates` at startup to incorporate any custom corporate certs mounted into `/usr/local/share/ca-certificates/custom/`. The `REQUESTS_CA_BUNDLE` or `SSL_CERT_FILE` environment variables are also respected by the `requests` library for custom CA bundles.

### 6. Docker container

The publisher runs inside a Docker container based on `python:3.14-slim`.

| Input | Mechanism |
|-------|-----------|
| `CONFLUENCE_URL` | Environment variable |
| `CONFLUENCE_SPACE` | Environment variable |
| `CONFLUENCE_PARENT_PAGE_ID` | Environment variable |
| `CONFLUENCE_LOGIN` | Environment variable |
| `CONFLUENCE_API_TOKEN` | Environment variable |
| `BANNER_REPO_URL` | Environment variable |
| `BANNER_PROJECT_NAME` | Environment variable |
| `PUBLISHER_MARKDOWN_ROOT` | Optional env (overrides `github_folder_with_md_files` when set) |
| `PUBLISHER_IMAGES_ROOT` | Optional env (overrides `github_folder_with_image_files` when set) |
| Custom CA certs | Mount to `/usr/local/share/ca-certificates/custom/` |
| Markdown source | Mount volume to `/data` (or set `PUBLISHER_MARKDOWN_ROOT`) |
| Images source | Mount volume to `/data_images` (or set `PUBLISHER_IMAGES_ROOT`) |

The entrypoint runs `update-ca-certificates` (to pick up any mounted custom certs), then executes `python publisher/main.py`.

### 7. Continuous integration

On push or pull request targeting `main`, the workflow builds the Docker image and runs the publisher container. Confluence connectivity and publish steps run only when the event is not a fork PR without secrets (guarded so fork PRs do not require Confluence credentials). Secrets are passed as `--env` flags to `docker run`.

### 8. Configurable banner

Created pages include an HTML banner pointing editors back to the Git repository. The banner is rendered from a template populated by `banner_repo_url` and `banner_project_name` (both configurable in YAML and overridable via environment variables).

## Design notes

- **Idempotent refresh model**: Each run deletes all property-tagged pages, then rebuilds from disk. There is no incremental diff against Confluence.
- **Migration from legacy pattern**: On first run after upgrade, a fallback search using the old text-based CQL (`text~{pattern}`) catches pages created by prior versions. Those pages are deleted and recreated with the new property-based tagging. The fallback can be removed in a later release.
